# PurposeBind

A reusable GenLayer Intelligent Contract that turns declared field metadata and information requirements into **minimum-cardinality field grants**. Semantic consensus determines coverage; deterministic set-cover enumeration determines exactly which field sets may be claimed.

No frontend, data custody, paid model API or application backend is required.

## Example

A public library dashboard needs weekly totals and their city names. The catalog offers a city/week aggregate table, visitor email addresses and staff birthdays. Validators independently classify all six field/requirement pairs. Only the aggregate table covers both requirements. The recipient can claim that table's identifier; adding emails is rejected by contract code.

Descriptions are synthetic metadata. The contract never receives, retrieves or releases actual visitor records. A downstream data service must independently enforce any resulting grant.

## Mechanism

1. A catalog owner registers immutable purpose, 1–4 requirements, 2–6 field descriptions and a distinct recipient wallet. Owner/ID namespaces prevent overwrites.
2. Either participant requests assessment. Leader and validators independently classify the complete ordered matrix as YES, NO or UNKNOWN. Each stored finding has exact field and requirement quotations. A separate validator audit checks quotation relevance against original metadata. All decision labels must agree.
3. Code enumerates up to 63 subsets and retains **all smallest field-count covers** using YES cells only. If allowing UNKNOWN could produce a smaller cover, or the only possible cover, the record is REVIEW. No possible cover is UNSATISFIABLE. Otherwise it is READY.
4. Only the named recipient can claim one exact canonical option, bound to its grant digest. Nonminimal sets, duplicates, supersets, altered digests and repeat claims fail. The owner cannot bypass the minimum-set rule.

State: REGISTERED → READY → CLAIMED, or REGISTERED → REVIEW / UNSATISFIABLE. Assessment and claim are one-way; correcting input requires a new ID. No appeal, edit, override or automatic retry is implemented.

UNKNOWN cells at the same minimum cardinality do not invalidate a proven YES-only option; those uncertain alternatives are simply not offered.

## API

Deploy `contracts/purpose_bind.py` without constructor arguments on **Stable Studionet, chain 61999**.

| Method | Arguments | Access |
|---|---|---|
| register | request_id, recipient, payload JSON string | Caller owns new record |
| assess | owner, request_id | Owner or recipient; REGISTERED |
| claim | owner, request_id, grant_digest, fields_json | Recipient; READY |
| get_record | owner, request_id | Public read; JSON string |
| get_protocol | none | Public read; `purposebind-1` |

Use `examples/library.json` as the payload. `fields_json` is a JSON array copied exactly from one returned option, preserving catalog order. All parameters are strings. See [PROTOCOL.md](PROTOCOL.md) for bounds, digests and integration rules.

## Verification

```sh
python -m unittest discover -s tests -v
pip install -r requirements-dev.txt
genvm-lint check contracts/purpose_bind.py
python scripts/prepare-sdk.py
python sdk-tests/check_sdk.py
npm ci
node scripts/read-live.mjs
```

The 18 protocol tests mock the host and model, including all 64 binary 3×2 coverage matrices. The separate SDK check uses real pinned SDK storage and calldata with mocked LLM responses. Neither establishes live consensus. `schema.json` is generated by the official GenVM linter.

Actual finalized receipts, addresses, source SHA-256 and persisted state are in [evidence/studionet.json](evidence/studionet.json). See [VALIDATION.md](VALIDATION.md) for observed results and coverage boundaries. `read-live.mjs` is read-only and requires no signing key. `verify-live.mjs` is an opt-in development harness, not a read-only check: it creates a dedicated zero-value run only with `PURPOSEBIND_NEW=1`, saves every hash before polling and resumes existing hashes. Do not run it merely to inspect the published deployment.

## Scope and limitations

- Minimizes **number of declared fields**, not bytes, sensitivity, privacy risk or legal obligations. A bundled field may contain more attributes than several narrow fields. This is not a privacy certification, consent system or compliance assessment.
- A YES cell means one field independently supplies that requirement from its description. Joins, transformations, complementary partial fields and inferred identifiers are unsupported; describe a prepared derived field explicitly instead.
- Inputs are owner-supplied assertions. Wallet signatures do not establish identity, data ownership, truth, independent parties or delivery rights. Validators do not inspect a real dataset or fetch links. Model error, correlated error and prompt injection remain possible.
- Grants are public metadata records. They transfer no tokens, keys, records or legal rights. Off-chain services must verify the configured source, owner, recipient, record and finality before delivery. They must check actual access authority separately.
- All metadata, quotations and findings are public and immutable. Submit only public or synthetic descriptions; never actual personal data, secrets or credentials.
- No expiry, revocation, field weighting, dynamic catalog updates, requester negotiation or cross-deployment deduplication. Recipient refusal can leave a READY record unclaimed. Storage is unbounded across IDs; each assessment is bounded to 24 cells.
